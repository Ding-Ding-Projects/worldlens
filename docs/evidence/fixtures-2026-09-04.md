# Large deterministic world fixtures and real Chunker round-trip proof

Evidence for two committed scripts:

- `scripts/fixtures/generate-measured-worlds.mjs` — generates the two large deterministic
  Anvil-format world fixtures via `@worldlens/worldgen`'s `generateMeasuredWorld`, writing
  a provenance JSON beside each world folder.
- `scripts/fixtures/round-trip-chunker.mjs` — copies a world, converts it through the real
  bundled Chunker CLI jar Java → Bedrock → Java, then streams a region-by-region semantic
  comparison (never a byte-equality check — Chunker legitimately rewrites bytes) via
  `scripts/fixtures/lib/anvil-reader.mjs`.
- `scripts/fixtures/negative-cases.mjs` — proves corrupt input, invalid configuration, a
  killed mid-conversion JVM, and an unwritable destination are all reported as failures.

All generation and conversion ran directly on this host, outside the repository, under
`C:\Users\cntow\AppData\Local\Temp\fixtures\`. Nothing here is simulated or estimated.

### Documented losses observed (all classified, none blind-whitelisted)

Three distinct, named categories, each derived from the actual data rather than
pattern-matched on message text alone:

1. **DataVersion format upgrade** (`3700 → 3837`) — Chunker's `JAVA_1_20_5` target writes
   DataVersion 3837 (Minecraft 1.20.5). Classified as documented only when the version
   moved *forward*, to exactly the DataVersion the round trip's own output actually
   carries (derived from the converted world itself, not a hand-maintained table) — a
   downgrade or an unrelated version number would still be flagged undocumented.
2. **`snowy` cosmetic-property normalization** — Java's `snowy=true/false` property on
   grass/podzol/mycelium is a *derived* render flag Minecraft recomputes from the block
   above; Bedrock has no equivalent stored property, so Chunker recomputes it on
   write-back. Classified by re-deriving, from the real per-block-name counts, that the
   *only* thing that moved between a section's before/after block-palette multiset is the
   `snowy` property distribution on an otherwise-identical block-name multiset
   (`classifyBlockMultisetDiff` in `lib/anvil-reader.mjs`) — any other multiset change
   (a block that actually vanished or changed) is left classified as undocumented.
3. **Heightmap re-encoding** (`WORLD_SURFACE`/`OCEAN_FLOOR`) — expected: Bedrock does not
   carry Java's exact packed heightmap encoding, so the packed longs differ after a round
   trip even when the underlying surface height is unchanged.

No block, biome, or chunk was silently dropped, duplicated, or moved.

## 3. Negative cases — verified at both the tiny dev scale and the 1 GB scale

Ran twice: once against a 96-chunk dev world (fast iteration) and once against the full
1 GB / 243,665-chunk fixture (`scripts/fixtures/negative-cases.mjs`). All four cases
correctly reported failure at both scales; **none was accepted on exit code 0 or a
non-empty output folder alone**.

| case | at 1 GB scale | how it was judged (not exit code alone) |
|---|---|---|
| corrupt input (truncated `r.0.0.mca`-equivalent region) | exit 0, `verdictIsFailure: true` | Chunker exited 0 but produced **no `region` directory at all** in its output — caught only because the script re-reads the *world* and finds 0 recoverable chunks against 243,665 in the pristine input, not because of the exit code |
| invalid `-c` converter-settings JSON | exit 1 | Chunker itself refused (Gson `MalformedJsonException`), no output produced |
| interrupted mid-conversion (`SIGKILL` at +150 ms) | exit `null`, signal `SIGKILL` | 0 chunks recoverable from the killed run's output; a killed JVM is never reported as success |
| unwritable destination (best-effort storage-exhaustion substitute) | exit 1 | Bedrock LevelDB open failed (`Database directory ... could not be created`); **documented limitation**: a genuine size-limited volume needs host-level privileges this lane does not have, so this substitutes an unwritable destination path exercising the same write-failure branch — recorded honestly as a substitute, not claimed as true disk-full coverage |

`allCorrectlyFailed: true` in both runs.

## 4. 10 GB fixture: real Chunker round-trip

**Status at the time of this report: NOT YET COMPLETE — retry in flight under the
orchestrator, not this lane, to avoid two Chunker jobs contending for the same disk.**

Sequence of what actually happened, recorded rather than smoothed over:

1. First attempt used `--timeout-ms 3000000` (50 minutes), sized against the *1 GB*
   fixture's measured leg time (347.5 s). The Java → Bedrock leg was still legitimately
   converting — `bedrock-out` held 2.19 GB of real, growing LevelDB output, no error in
   its stderr — when the harness's own `SIGKILL` fired at the 50-minute mark. Verdict
   recorded: `java-to-bedrock-failed` with `timedOut: true`. **This was a harness limit,
   not a Chunker failure**, and is now called out explicitly by the `-harness-timeout`
   verdict variants added below.
2. `round-trip-chunker.mjs` was fixed in place (same commit as this doc):
   - The per-leg timeout now auto-scales from the source world's real on-disk bytes -
     `max(50 min, 15 min per source GB)` - unless the caller pins one explicitly via
     `--timeout-ms` or the new `--timeout-minutes`. A 10 GB world therefore gets at least
     150 minutes per leg by default instead of the fixed 50 minutes that killed it.
   - `outputBytes` is now measured from disk unconditionally (killed, failed, or
     succeeded), not only on a clean exit - a killed leg's real partial output is exactly
     the evidence a reader needs, and reporting 0 for it would hide that.
   - The verdict distinguishes `java-to-bedrock-harness-timeout` /
     `bedrock-to-java-harness-timeout` from an actual Chunker failure exit code.
3. A second attempt was started locally with a 2-hour timeout, then **deliberately
   killed** (`Stop-Process` on both the orchestrating `node` and the spawned `java`, both
   verified gone) partway through its Java → Bedrock leg, and its scratch directory
   removed, because the orchestrator was starting its own rerun with a 4-hour timeout and
   two simultaneous Chunker conversions against the same 10 GB world on one shared disk
   would only slow both down and risk corrupting neither one cleanly. No half-finished
   output from this lane's second attempt was left on disk.

### 4a. A later retry (`roundtrip-10gb-r3`) got both Chunker legs clean, then the *comparison* segfaulted

Both Chunker legs succeeded on this retry: Java → Bedrock produced 3.5 GB of Bedrock
output, and Bedrock → Java converted it back to 9.4 GB / 2,380 regions — matching the
source fixture's region count. Then, part-way through the streamed region-by-region
comparison, the Node process itself died with `Segmentation fault` (exit code 139) —
not a JS exception, a native crash, roughly 1h44m into the comparison step and with no
`evidence.json` written, throwing away the evidence of two multi-hour Chunker legs that
had already succeeded.

**Root cause: `missingChunks`/`extraChunks` were unbounded for the whole run**, unlike
every other recording array in the comparison. `documentedLossSample`,
`undocumentedDifferences` and the per-chunk difference lists were already capped at
`MAX_RECORDED_UNDOCUMENTED` (500), but the two chunk-key lists were pushed onto with no
limit for the entire multi-million-chunk streamed comparison — on top of whatever
garbage the per-chunk NBT decoding already produces every iteration, this is unbounded
heap growth in precisely the pass that runs longest and allocates hardest, which is
exactly the shape of thing that turns a slow leak into a native crash instead of a clean
`FATAL ERROR: JavaScript heap out of memory` (the latter is what an out-of-heap V8 abort
normally looks like; a raw `SIGSEGV` is the signature of memory pressure spilling past
what V8's own guard rails catch).

**Fix (this repository, same commit as this doc update):**

- Every recording list in the comparison (`missingChunks`, `extraChunks`,
  `documentedLoss`, `undocumented`) now goes through one `boundedRecorder(maxRecorded)`
  helper in `round-trip-chunker.mjs`: it keeps at most `maxRecorded` real entries but
  always reports the true total count offered to it, so truncation is visible in the
  evidence rather than silently changing what "total" means.
- The streaming comparison itself was extracted into an exported `compareWorlds(before,
  after, { maxRecorded })`, callable directly against two already-converted world
  folders without running Chunker at all — reused both by `roundTripAndCompare` and by
  the new `--compare-only` mode below, and directly unit-testable (see §6) without
  needing the real Chunker jar or hours of runtime.
- New `--compare-only` mode: `node scripts/fixtures/round-trip-chunker.mjs
  --compare-only --work <existing-work-dir> --out <evidence.json>` re-runs only the
  comparison against a `--work` directory's `java-original-copy` and `java-back-out`
  from an earlier full run, running no Chunker leg at all. This exists specifically so a
  comparison-step crash never has to throw away hours of already-succeeded Chunker
  conversion. Its evidence records the legs as `reused: true` with their on-disk byte
  sizes; per-leg timing/exit code from the original run is not recoverable from the
  directories alone and is reported honestly as unavailable rather than guessed.

**Command used to attempt recovery of this section** (no Chunker re-run, no
regeneration; the two already-converted legs on disk under `roundtrip-10gb-r3` were
left untouched throughout):


## 5. What broke and was fixed along the way (worth recording, not hiding)

The first attempt at the 1 GB round trip **crashed the node process** (a native V8 crash,
not a clean exception) during the comparison step. Root cause: the original comparator
loaded the *entire* decoded chunk set of both the original and round-tripped worlds
(243,665 chunks each, fully decoded NBT objects) into two JS `Map`s simultaneously before
comparing — workable for the tiny dev fixture, not for a quarter-million chunks twice.

Fix: `forEachRegionPair` in `lib/anvil-reader.mjs` streams the comparison one matched
region-file pair at a time (~2,048 chunks in memory at any moment, not 487,330). Re-ran
the small-world tests (all green) and then the full 1 GB round trip, which completed with
peak RSS around 464 MB. This is the reason `round-trip-chunker.mjs` no longer calls
`readWorldChunks` (which still exists, documented as safe only for small worlds, and is
what the focused unit tests use).

A second, related crash happened later at the 10 GB scale even with the streaming fix in
place: streaming bounds *chunks held at once*, but two of the comparison's own recording
arrays (`missingChunks`, `extraChunks`) had no bound on their *total length* across the
whole run — see §4a for the root cause and fix (bounded recording via `boundedRecorder`,
plus the new `--compare-only` mode that can recover a comparison without re-running
Chunker).
